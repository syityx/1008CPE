# Wi-Fi与CPE双链路文件循环下载

默认启动方式已改为文件下载。发送端提供文件，接收端通过Wi-Fi和CPE两路请求文件块，在本机按顺序合并并校验，再循环下一文件。云端仍为47.97.248.31，沿用UDP30006/30007、公开实验token和自动地址发现，无需修改服务器配置或填写两端IP。

## 怎么连接、怎么启动

两台电脑安装Python 3.10或更新版本，下载完整仓库。

1. 发送电脑连接路由器Wi-Fi。
2. 接收电脑网线连接CPE，同时直接连接同一Wi-Fi，或通过手机USB共享该Wi-Fi。手机共享Wi-Fi时关闭移动数据，确认另一条链路确实经过CPE。
3. 发送端双击 `send/start.cmd`，接收端双击 `receive/start.cmd`，允许Windows管理员提示。
4. 接收端显示 `注册LAN/CPE=True/True` 后自动开始：small.txt（1 MB）→ medium.txt（3 MB）→ large.txt（5 MB）→ 重复。
5. 不需要启动VLC。按接收端窗口中的Ctrl+C停止并保存记录；发送端可以继续等待下一次接收。

发送端首次启动时，若 `send/files` 为空，会自动生成三个测试文件；已有文件不会覆盖。使用自己的文件时，把1至8个文件放进该目录。默认小/中/大优先，其余按文件名排序；运行中请勿修改源文件，修改后重启两端。

网卡自动识别与路由方式沿用1008CPE：云目标经CPE，发送端目标经Wi-Fi/USB；存在多个候选网卡时按提示选择。两端应能通过Wi-Fi局域网互通，路由器客户端隔离会阻止这一路。

## 文件链路

```text
接收端请求方向：
  Wi-Fi：接收程序 → Wi-Fi/手机USB → 发送端文件服务
  CPE： 接收程序 → CPE → 阿里云UDP30007 → 发送端已建立的UDP映射 → 文件服务

文件内容返回方向：
  Wi-Fi：发送端 → Wi-Fi/手机USB → 接收程序
  CPE： 发送端 → 阿里云UDP30006 → 云端UDP30007 → CPE → 接收程序

接收程序：双路文件块 → 按文件位置合并 → SHA256校验 → 保存 → 下一文件
```

发送端定期向云端公告LAN地址并保持UDP映射；接收端通过CPE注册获取该地址，再向发送端发起LAN注册。CPE侧文件请求由云端转交发送端，回复沿接收端的注册映射返回。无需SSH隧道、HTTP服务或新增云端端口，云端不保存源文件。

## 下载策略和可靠性

- 默认使用1008CPE原模糊PID计算方法，控制器放在接收端。原规则表、整数输出、20单位窗口、暖机>10和 `G=clip(5+4.5*u,0,10)` 保留；一个调度单位改为一个文件块。
- 默认32 KiB文件块，块再拆为不超过1200字节的UDP片。按原规则 `位置<G` 分配到CPE路径，初始G=5。
- 每路一个在途文件块；已排队、在途和待合并的总窗口默认32块。快的一路不抢另一队列的块。
- PID反馈是两路已完成、等待按序写入的块数，约100ms补采。控制器每次接收实验重置一次，跨文件/轮次连续运行。
- 缺片在同一路重传，默认每次等待1秒、最多重试5次。不同块和轮次使用不同请求标识，拒绝迟到混入；超出重试次数会报错，不跳过缺块。
- 完整文件必须大小和SHA256同时一致。UDP丢片可补传；文件损坏、源文件变化或持续断路会终止实验。
- 默认发送端每8个小片暂停一个批次间隔，避免大量UDP突发。实际等待精度受操作系统影响，可在send/config.json调整file_burst_packets和file_burst_interval。

这是沿用UDP链路的可靠文件下载实验。分流比例控制文件块数；块大小、可靠重传和反馈节奏与原视频实验不同，不能直接当作相同实验条件。

在管理员终端可选参数（通常双击启动即可）：

```powershell
python receive/files.py --mode fixed --rounds 1
python receive/files.py --mode fuzzy --duration 60
python receive/files.py --block-kib 64 --rounds 3
python send/files.py --files-dir "D:\要下载的文件"
```

fixed为固定五五；fuzzy为原PID。轮数0与时长0表示不限，默认二者为0，持续循环到Ctrl+C。config.json中同名file_参数可预设；原IP命令行覆盖参数继续可用。

## 下载结果

接收端每次在 `receive/results/日期时间_编号/` 新建目录：

- `downloads/`：每类文件的最新完整副本；未完成内容保留为 `.part`。
- `files.csv`：轮次、文件大小、已写入字节、耗时、SHA256和完成/中止/失败状态。
- `blocks.csv`：各块的路径、大小、重试和耗时。
- `throughput.csv`：约200ms采样的两路接收字节、速率、待合并块数与G。
- `control.csv`：调度单位数、PID周期、缓存输入、G和更新次数。
- `config.json`、`summary.json`：本次配置、清单与最终汇总。

接收字节/速率包括重复片和重传片正文，不含UDP/IP/HMAC头；完整文件有效字节见files.csv。无限循环会持续增加CSV记录，但完整文件只保留每类最新副本。个人源文件与下载/记录目录已加入.gitignore。

## 原视频模式参考

原视频代码保留在send/main.py和receive/main.py。双击两端的 `start_video.cmd` 可运行原VLC实验，文件与视频模式不能同时占用同一套端口。以下为原视频方式的说明。

本工程使用原模糊PID分流与按序合流算法。发送端接入Wi-Fi；接收端同时接入同一Wi-Fi（或手机USB共享该Wi-Fi）和CPE以太网。

云服务器 **47.97.248.31** 的中继已部署为常驻服务，两端和云端配置已同步。仓库包含可直接使用的 `config.json`，无需登录服务器、填写云地址或生成token。

```text
发送端VLC -> 本机127.0.0.1:49998 -> 分流器
  链路0：发送端Wi-Fi -> 接收电脑Wi-Fi -> 合流器
     或：发送端Wi-Fi -> 手机Wi-Fi/NAT -> 手机USB -> 合流器
  链路1：发送端Wi-Fi/互联网 -> 阿里云:30006 -> 云端:30007
                              -> 运营商/CPE -> 接收电脑以太网 -> 合流器
合流器 -> 本机127.0.0.1:60001 -> 接收端VLC
```

## 下载后怎么启动

两台电脑安装Python 3.10或更新版本（启用py启动器或加入PATH），并各自下载整个仓库。全部Python代码仅用标准库，没有第三方库依赖。保留完整目录结构，不能只复制main.py。

1. 发送笔记本连接路由器Wi-Fi。
2. 接收电脑网口连接CPE；另一路直接连接同一路由器Wi-Fi，或用手机USB共享该Wi-Fi。使用手机时确认共享的是Wi-Fi，关闭手机移动数据以便验证实验链路。
3. 发送端双击 `send/start_video.cmd`，接收端双击 `receive/start_video.cmd`。Windows会弹出管理员确认，用于开放实验UDP入站；接收端还会配置临时路由。
4. 等待接收端显示 `注册LAN/CPE=True/True`。接收端VLC打开 `udp://@:60001`。
5. 发送端VLC将视频通过UDP推送到 `127.0.0.1:49998`，使用MPEG-TS封装，单个负载不超过1316字节（常见7×188字节TS包）。

启动顺序可以调换。发送端会周期公告自己的Wi-Fi地址；接收端从云端获取后，通过LAN独立注册，链路0的视频仍直接回传到接收端。没有视频输入时发送端收包计数为0是正常的。

程序自动读取IPv4、网关和网卡编号，优先识别Wi-Fi、当前CPE网关 `192.168.2.230`，排除VMware/WSL等虚拟接口。接收端只有CPE和手机USB两张有效网卡时无需选择；存在多个候选时按窗口提示选择实际接口。CPE默认网关改变时可能需要选择对应网卡。

接收端自动添加两个目标的 `/32` 临时路由：云地址经CPE；发送端地址经Wi-Fi或手机USB。直接Wi-Fi同网段时直连；手机USB不同网段时经手机网关。不修改默认网关；临时路由重启后失效，下次启动会重新设置。已有相同路由会复用；遇到冲突路由会报错，需核对现有设置。

## 固定配置与token

- 云地址：`47.97.248.31`；UDP30006为视频入口，UDP30007为注册、地址发现和回传。
- LAN：发送端UDP30002；接收端LAN UDP30002、CPE UDP30006。
- 本机接口地址与发送端地址默认为 `auto`，启动时检测，不需要每次修改文件。
- 三端共享公开实验token：`1008CPE-lab-public-token-20261008`。它用于匹配当前实验并保留原HMAC报文格式；由于公开，不提供防伪认证，也不加密视频。SSH私钥与此token无关，不进入仓库。

`initialize_config.py` 现在只在配置文件缺失时从模板补齐固定配置：运行 `python initialize_config.py` 即可。正常下载已有配置，不必运行。它不生成新的随机token，不覆盖已有文件，也不需要手工将token复制到云端。

本服务同时服务一组发送端和接收端，后注册的同实验接收端会替换前一个。不要同时开多个接收端或在正式实验期间运行cloud_probe。

## 保留的原算法

视频包为 `[media:uint8][sequence:uint32大端][原视频负载]`；media=0为局域网，media=1为云端/CPE。每组10包按 `位置 < G` 分到链路1，初始G=5。统计窗口为20包、暖机条件为窗口计数>10。模糊规则表、0.01误差缩放、PID增益限幅、整数输出和 `G=clip(5+4.5*u,0,10)` 保留。原代码已关闭的随机容量限制不再保留。

缓存反馈仍为 `[121:uint8][count0:uint16][count1:uint16]`，count0/1分别对应链路0/1，由LAN注册socket返回。默认反馈20ms、保活3s、注册有效期15s。断开LAN会失去反馈，G保持最后值。

合流采用优先序号队列，距离上次输出超过100ms时跳过缺失序号。增加迟到/重复丢弃、32位回绕、有限队列和异常退出，并修复原双队列错位问题。发送端重启序号从0开始，接收端也应重新启动。

云端只为链路1视频去除36字节信封，然后从UDP30007原样回传。局域网和云端均通过接收端主动注册建立回程，不要求手机/CPE端口映射；网络需允许向注册的同一对端回包。

原模糊PID粒度较粗，例如u=1得到G=9.5，会让10个包全部走链路1。验证网络时可在发送端用 `python send/main.py --fixed-g 5` 临时固定一半一半；正式运行不加该参数。

## 验证和故障定位

运行 `python test_experiment.py`。测试包含自动/手动发送端地址下的300包双路合流、地址公告过期与非法报文、USB/直接Wi-Fi出口规划、配置补齐、原PID参考结果以及排序超时/重复/回绕。

本地测试证明程序逻辑，完整双机VLC播放仍需在实际两台电脑上验证。`True/True`证明注册成功；核对路由或依次断开接口，可进一步确认两路视频各自经过对应网络。

- LAN注册失败：检查两端是否接入同一Wi-Fi、手机是否支持共享Wi-Fi、路由器客户端隔离和发送端防火墙。先确认发送端窗口显示云端已记录LAN地址。
- CPE注册失败：检查CPE上网、云端UDP30007和目标路由。云端常驻服务正常时不需要手动启动。
- CPE注册成功但无视频：检查发送端云端发送计数、云端UDP30006和接收端链路1计数。
- 视频卡顿：检查跳过/迟到/溢出计数，降低VLC码率；公网抖动较大时可调整排序超时。

需要指定接口时，在管理员终端使用 `python receive/main.py --lan-ip 接收端局域网IPv4 --cpe-ip 接收端CPE侧IPv4 --sender-ip 发送端WiFiIPv4`。发送端可用 `--lan-ip` 指定Wi-Fi地址。正常启动不需要这些参数。
